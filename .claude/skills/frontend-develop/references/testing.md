# Testing — 요구사항을 지키는 테스트

## 1. 목적과 최우선 원칙

테스트는 **승인된 요구사항과 사용자가 기대하는 관찰 가능한 동작을 검증하는 실행 가능한 계약**이다. AI의 구현 결과를 정당화하거나 CI를 녹색으로 만들기 위한 도구가 아니다.

- 테스트 기대값의 출처는 개발자가 승인한 기능 명세, API·컴포넌트 계약, 결정된 예외 처리 규칙이다. **구현 코드의 현재 결과를 그대로 복사해 정답으로 삼지 않는다.**
- 테스트의 통과보다 요구사항 충족이 우선이다. 실패하면 구현 결함, 명세 불일치, 테스트 결함, 환경 문제를 구분한다.
- 새 테스트 작성은 **현재 승인된 작업 범위 안에서만** 허용한다. 무관한 코드나 다른 Row/기능의 테스트를 선제적으로 추가하지 않는다.
- **저장소에 존재하는 테스트 코드의 수정·삭제·비활성화·기대값 변경에는 개발자의 사전 승인이 필수다.** 테스트 통과를 위해 임의로 완화하지 않는다.
- 테스트의 개수·커버리지 수치·녹색 표시보다 **결함 검출력, 결정성, 신뢰성, 유지보수 비용**을 우선한다.

## 2. 테스트 범위와 도구

| 구분 | 검증 대상 | 도구 및 방법 |
| --- | --- | --- |
| 컴포넌트 동작 | 사용자의 클릭·선택·입력, 상태·이벤트·오류·접근성 관련 동작 | Vitest + React Testing Library (도입 시), 실제 사용 시나리오 중심 |
| 순수 함수·업무 로직 | 계산·변환·분기, 경계값, 오류 처리, 불변조건 | Vitest (도입 시), 입력 대비 결과 중심 |
| 정적 검사 | 타입 정합성, 컴파일 단계 오류 | 기존 `npm run typecheck` (`tsc --noEmit`) |
| 브라우저·OS 의존 동작 | 반응형, 포커스·키보드, Native Select 등 실제 브라우저 동작 | 필요성이 확인된 경우 브라우저/실기기 검증 별도 선택 |

- 현재 저장소의 `package.json`에는 Vitest와 React Testing Library가 설치되어 있지 않다. **이 문서는 도입·설치를 승인하거나 완료한 상태를 의미하지 않는다.**
- 변경 영향과 위험에 비례해 필요한 계층만 테스트한다. 모든 함수·컴포넌트에 일률적으로 테스트를 강제하지 않는다.
- UI 구조만 변경한 경우에는 기존 동작 보존을 우선 검증한다. 복잡한 라이브러리(예: AG Grid)의 내부 기능을 프로젝트 테스트에서 재구현하지 않는다.
- React Testing Library는 실제 사용자 관점의 DOM/접근 가능한 요소로 검증한다. 내부 state, private 함수 호출 횟수, CSS 구현 세부에 과도하게 결합하지 않는다.
- jsdom의 시뮬레이션을 iOS/Android 네이티브 선택 UI의 실기기 검증으로 간주하지 않는다.

## 3. 요구사항 기반 TDD 흐름

1. **명세 확인:** 작업 대상, 정상 동작, 경계조건, 실패 시 동작과 개발자 승인 여부를 확인한다. 불명확한 기대값을 AI가 임의로 확정하지 않는다.
2. **사례 선정:** 위험도가 높은 정상 경로와 의미 있는 실패·경계 사례를 선정한다. 테스트 이름은 입력·행동·기대 결과가 드러나게 작성한다.
3. **Red:** 구현 전에 가능한 범위에서 실패하는 테스트를 작성하고, 기대한 이유로 실패하는지 확인한다. 이미 구현된 기능은 회귀 테스트를 작성하되 **기존 구현이 곧 명세라고 가정하지 않는다.**
4. **Green:** 기능 코드를 수정해 명세를 만족시킨다. 테스트 값을 낮추거나 검증을 제거해서 녹색으로 만들지 않는다.
5. **Refactor:** 동작을 유지하면서 현재 승인된 작업 범위 안에서만 정리한다. 기존 테스트 변경이 필요하면 먼저 승인을 받는다.
6. **검증·보고:** 관련 테스트 및 기존 타입 검사를 가능한 범위에서 실행하고 결과와 미실행·실패 사유를 구분한다.

TDD 순서를 기계적으로 흉내 내는 것보다 **요구사항이 테스트보다 먼저 결정되어 있는지**가 중요하다. 테스트를 나중에 추가하더라도 명세를 독립적으로 확인해야 한다.

## 4. 좋은 테스트의 최소 기준

- **의미:** 이 테스트가 실패하면 어떤 사용자 요구사항이나 계약이 깨졌는지 설명할 수 있어야 한다.
- **검증력:** 올바른 구현뿐 아니라 대표적인 잘못된 구현에서도 실패하도록 핵심 결과를 단언한다. `expect(true).toBe(true)`, 무의미한 렌더링 확인, 테스트 대상 자체를 Mock 처리하는 행위를 금지한다.
- **분리:** Arrange(준비) → Act(행동) → Assert(검증)를 구분하며, 하나의 테스트가 다루는 행위와 실패 이유를 명확히 한다. 여러 assertion은 동일한 동작 검증에 필요한 경우 허용한다.
- **결정성:** 실행 순서·외부 네트워크·실제 시간·랜덤 값·다른 테스트의 상태에 우연히 의존하지 않는다. 테스트 간 공유 상태를 격리·초기화한다.
- **현실성:** UI 이벤트는 가능한 실제 사용자 조작 경로로 실행하고 접근 가능한 역할·이름·라벨을 기준으로 요소를 찾는다. `data-testid`는 적절한 의미 기반 조회가 어려울 때만 사용한다.
- **격리 수준:** 테스트 범위 밖의 API, 시간, 스토리지 등의 불안정한 경계만 필요할 때 대역으로 대체한다. **Mock 반환값만 확인해 프로덕션 로직을 검증한 척하지 않는다.**
- **보수성:** 거대한 Snapshot을 무분별하게 추가하거나 변경된 Snapshot을 검토 없이 갱신하지 않는다. 사용자에게 중요한 상태·문구·동작은 명시적으로 검증한다.
- **유지보수:** 중복 설정은 필요한 만큼만 공통화하며, 테스트가 구현 세부 변경마다 깨지지 않도록 공개 계약에 집중한다. 불필요한 타이머 대기·재시도·비결정적인 sleep을 피한다.
- **선택과 집중:** 최소한 정상 흐름, 중요한 경계값, 실제로 발생 가능한 실패 흐름을 우선한다. 단순 전달 함수와 외부 라이브러리의 이미 보장된 내부 동작까지 중복 테스트하지 않는다.

## 5. 기존 테스트의 변경 보호 — 승인 필수

**기존 저장소 테스트는 개발자 승인 없이 손대지 않는다.** 다음 행위는 모두 변경에 해당한다.

- assertion의 기대값 변경·삭제·약화, 테스트 내용·픽스처·Mock·설정 변경
- 테스트 파일 삭제·이동·이름 변경, Snapshot 갱신
- `skip`, `todo`, `only`, `describe.skip`, 조건부 생략, CI 제외, Mock 우회 등 테스트를 실행하지 않거나 통과처럼 보이게 하는 조치

**신규 테스트가 없는 영역**에서는 승인된 기능 범위에 한해 새 테스트를 추가할 수 있다. 기존 테스트와 충돌하거나 이미 존재하는 테스트를 변경해야 한다면 다음 절차를 따른다.

1. 실패한 테스트/파일/시나리오와 재현 결과를 제시한다.
2. **구현 버그 / 승인된 명세 변경 / 테스트 자체의 오류 / 환경·플레이키 문제** 중 원인을 분류하고 증거를 제시한다.
3. 구현 버그라면 기존 테스트를 유지하고 허용된 범위에서 **구현을 고친다**. 범위를 벗어나면 승인을 요청한다.
4. 명세가 변경되었다면 변경 전·후 계약, 영향 받는 테스트 목록, 수정·삭제·비활성화 각각의 대안을 제시하고 **명시적인 개발자 승인 후** 반영한다.
5. 승인이 없거나 판단이 불확실하면 기존 테스트는 유지하고 실패를 그대로 보고한다. 통과했다고 보고하지 않는다.

### 기능 제거로 인해 기존 테스트가 실패할 때

- 먼저 해당 기능이 **공식적으로 제거 승인된 범위**인지 확인한다. 임의로 기능이 없어진 것으로 간주하지 않는다.
- 제거가 승인되었다면 관련 테스트를 목록화하여 **일괄 삭제 승인**을 요청할 수 있다. 미승인 상태에서는 삭제하지 않는다.
- 이력 보존이 필요하면 `skip`/`todo` 등 비활성화와 사유·관련 이슈·재검토 조건을 **대안으로 제안**할 수 있다. **승인 없이는 설정하지 않는다.**
- 비활성화된 테스트는 검증에 성공한 테스트가 아니라 **실행되지 않은 테스트**다. CI·완료 보고에 `skipped/todo` 개수와 사유를 별도로 남겨 추적한다.
- 테스트를 무력화해 성공 결과를 만드는 것보다, 실패 원인을 명시하고 작업을 멈추는 편이 낫다.

## 6. AI가 해서는 안 되는 행위

- 실패를 없애려고 기대값을 현재 구현 결과에 맞게 고치기
- 검증 범위를 줄이거나 Mock·fixture를 바꿔 오류 경로를 숨기기
- 테스트를 주석 처리하거나 생략 처리해서 전체가 통과한 것처럼 보고하기
- 외부 의존성을 전부 Mock 처리해 실제 로직을 테스트하지 않기
- 테스트를 통과시키기 위해 현재 요청 범위 밖의 기능·아키텍처를 수정하기
- 테스트를 실행하지 않았거나 실패했는데 통과·완료라고 보고하기

## 7. 실행·완료 보고 기준

- 코드 변경 전 명세와 검증 항목을 간단히 정리한다.
- 해당 기능의 새/관련 테스트만 우선 실행하고, 환경이 준비되어 있다면 타입 검사 등 영향 범위의 검증을 수행한다.
- 보고에는 **실행한 명령, 통과·실패·비활성화 수, 미실행 사유, 남은 위험, 승인 필요 사항**을 구분한다.
- 테스트 도구가 없는 상태에서 테스트 실행 성공을 주장하지 않는다. 설치와 설정은 별도 지시가 있을 때만 한다.
- **커버리지 100%, 테스트 건수 등 허수 지표를 목표로 하지 않는다.** 위험도가 높은 요구사항을 실제로 보호하는지가 완료 판단 기준이다.
- 현재 프로젝트의 **Notion Row 단위 작업·개발자 컨펌 흐름**과 Git 브랜치 승인 절차를 우선한다. 테스트 통과가 개발자 승인을 대신하지 않는다.
